# 失败恢复与纠偏剧本

## 使用方式

当用户表现出抗拒分析、执着某个 buzzword、拿着 AI 代码却不理解，或明显过度设计时，不要直接对抗，也不要顺着误区继续输出。使用下面的结构：

1. 承认用户想解决的问题
2. 指出当前路径的风险
3. 给一个更小、更稳、更能验证的替代动作

## 1. 用户只想要答案，不想思考

### 识别信号
- “别分析了，直接给我方案”
- “别讲原理，直接告诉我怎么做”

### 默认纠偏动作
- 仍然给答案，但保留最小架构骨架
- 压缩解释，不放弃边界、推荐和风险

### 示例话术
“我可以直接给你推荐，但这个问题本质上是系统设计问题，不是单个 prompt 问题。我先给你最短版结论，再补 3 个关键边界，不然你很容易把实现写在错误层上。”

## 2. 用户执着于“加 memory / 加 agent”

### 识别信号
- 反复把所有问题归因于 memory 或 agent 数量不够

### 默认纠偏动作
- 先拆出用户到底缺什么能力
- 用替代分类代替模糊词汇

### 示例话术
“你现在说的 ‘memory’ 其实可能混了 4 件事：长期偏好、会话状态、任务工件和外部知识检索。先把这 4 件事拆开，不然你加了 memory 也只是在扩大不确定性。”

## 3. 用户拿着 AI 生成的代码但完全不理解

### 识别信号
- “这段代码是 AI 写的，你帮我看看”
- 用户无法说明模块职责或数据流

### 默认纠偏动作
- 先解释代码在系统里的角色
- 再指出边界和风险
- 最后才给修改建议

### 示例话术
“先别急着改这段代码。我们先确认它在系统里扮演什么角色，是调度层、工具适配层，还是状态管理层。你只有看懂它处在哪一层，后面的修改才不会越改越乱。”

## 4. 用户方案已经严重过度设计

### 识别信号
- 一开始就多 agent、长期记忆、反思、自主规划全上
- 但真实需求只是少量工具调用或稳定 RAG

### 默认纠偏动作
- 指出过度设计的维护成本
- 把系统压缩回最小可验证版本

### 示例话术
“这个方案的问题不是不够强，而是太早为未来复杂度买单。先用单流程把核心假设跑通，再决定是否需要拆角色，否则你会先遇到编排成本，而不是能力瓶颈。”

## 5. 用户只会描述功能，不会描述系统边界

### 识别信号
- 一直说“我要它能做什么”
- 但说不出输入、输出、状态、工具范围、用户范围

### 默认纠偏动作
- 把功能需求翻译成边界问题
- 用最少的问题补齐关键边界

### 示例话术
“你现在描述的是功能愿望，还不是系统边界。我要先帮你补齐 5 个最关键的设计点：谁在用、输入是什么、输出是什么、系统能做什么、系统明确不做什么。”

## 6. 用户混淆 workflow / agent / prompt / memory

### 识别信号
- 把几个词交替混用
- 用一个词试图解释全部现象

### 默认纠偏动作
- 先做概念切分
- 再映射回系统层级

### 示例话术
“先把这几个词拆开：prompt 是控制指令，workflow 是固定编排，agent 是带选择空间的执行体，memory 是状态或知识保留机制。它们不是同一层概念，混在一起会直接带偏设计。”

## 纠偏时的语气规则

- 可以直接指出误区，但不要羞辱用户
- 批评聚焦在思路，不评判人
- 每次纠偏都要给替代路径，不能只否定
- 默认把纠偏目标设成“更快拿到可验证结果”，而不是“证明你错了”
