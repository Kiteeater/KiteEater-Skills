# 标准输出模板

## 默认完整模板

```md
### 1. 问题重述
把用户原始表述翻译成更精确的系统目标。明确这不是“做个 X”，而是“要解决哪类系统问题”。

### 2. 本质拆解
- 目标是什么
- 系统边界是什么
- 输入 / 输出是什么
- 关键状态是什么
- 哪些部分应该交给模型，哪些交给规则 / API / 工具 / 检索

### 3. 架构方案选项
至少给 2 个可行方案。每个方案都讲：
- 适用前提
- 优点
- 缺点
- 容易失败的地方

### 4. 推荐方案与理由
明确给出推荐，不只平铺选项。
必须回答：
- 为什么推荐这个
- 为什么现在不推荐另一个
- 这个选择最重要的 trade-off 是什么

### 5. 模块设计
- 模块划分
- 每个模块的职责
- 状态与数据流
- 工具 / 检索 / memory / evaluator 在哪里

### 6. 关键风险 / Failure Modes
至少指出 3 个关键风险，并说明：
- 为什么会发生
- 会造成什么后果
- 应该如何监测或缓解

### 7. MVP 路线
- 第一版只做什么
- 明确不做什么
- 先验证哪条关键假设
- 先接哪几个接口或工具

### 8. 评估方式
- 看什么指标
- 用什么测试集 / 场景
- 如何区分 prompt 偶然性和系统性改进

### 9. 这次你应该学会的知识点
提炼 1-3 个知识点，不要贪多。

### 10. 下一步练习建议
给一个小练习，让用户能自己做一次类似判断。
```

## 评审型模板

```md
### 1. 问题重述
把用户现有方案还原成系统设计问题。

### 2. 主要 Findings
按严重度列出结构性问题，而不是先改措辞。

### 3. 为什么这些问题会发生
指出误区、边界缺口、状态缺失、评估缺失或过度设计来源。

### 4. 修正方向
给出更稳妥的设计重组建议。

### 5. 关键风险 / Failure Modes
说明如果不修，会在什么场景爆出来。

### 6. MVP 修正路线
优先改什么，先不改什么。

### 7. 学习点
提炼这次 review 对应的架构原则。

### 8. 下一步练习
给用户一个自查动作。
```

## 概念型压缩规则

概念型问题中，可以压缩：
- 模块设计
- MVP 路线
- 实现展开

概念型问题中，不能省略：
- 这个概念解决什么问题
- 系统边界
- 何时该用 / 何时不该用
- 与相邻概念的区别
- failure mode 或常见误区

## Implementation Gate 模板

当用户要求直接实现但门禁未过时，用下面的结构回应：

```md
现在不建议直接进入实现，因为还缺少这些架构前提：
- ...
- ...

先补齐这几个点：
1. ...
2. ...

补齐后再进入实现，会比现在直接写代码更稳，因为：
- ...
```

## 推荐表达规范

推荐方案时，必须显式写出：
- “我推荐 X，不推荐直接上 Y”
- “核心原因是 ...”
- “主要 trade-off 是 ...”

不要用含糊表达替代推荐，例如：
- “都可以”
- “看情况”
- “可以先试试”

如果真的取决于条件，也要明确说出条件分界线。

## Completion Criteria

回答只有满足下面 6 条才算合格：
- 已转译为系统问题
- 已给推荐而不是只列方案
- 已讲清主要 trade-off
- 已指出关键 failure mode
- 已给下一步建议
- 已提炼学习点
