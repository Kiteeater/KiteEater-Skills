# 反模式识别与纠偏

## 纠偏总规则

每次检测到反模式时，使用固定三步：

1. 点明误区
2. 解释为什么会出问题
3. 提供更合理的替代框架

不要只说“不对”。要说清楚“不对在哪里、会坏成什么样、应该怎么替换”。

## 1. 把 prompt 当架构

### 识别信号
- 用户反复问“prompt 怎么写得更强”
- 用户把系统失败归咎于提示词不够长
- 用户没有提边界、工具、状态、检索、评估

### 纠偏
- 误区：你把 prompt 当成系统设计本身了
- 为什么会出问题：prompt 能影响行为风格，但不能替代状态管理、工具可靠性、检索质量和评估闭环
- 替代思路：先拆系统边界，再决定 prompt 只是哪个模块的控制层

## 2. 把 workflow 当 autonomous agent

### 识别信号
- 用户描述的是固定步骤，但坚持叫它 agent
- 每一步都被预先定义，没有真正的开放式决策

### 纠偏
- 误区：你需要的可能是 workflow，不是 autonomous agent
- 为什么会出问题：把固定流程包装成 agent 会增加调试难度，却不增加真实能力
- 替代思路：先判断流程是否真的需要动态规划与自主决策，否则用 workflow 更稳

## 3. 把 memory 当万能解

### 识别信号
- 用户把“回答不稳定”“上下文丢失”“效果差”统一归结为没 memory

### 纠偏
- 误区：memory 不是统一补丁
- 为什么会出问题：你可能缺的是检索、任务状态、缓存、用户画像或结构化上下文，而不是一个模糊的大 memory
- 替代思路：先区分长期偏好、会话状态、任务工件、检索知识和缓存，再决定是否要 memory

## 4. 默认上多 agent

### 识别信号
- 用户一开始就要 planner + executor + critic + reviewer + memory agent
- 没有先证明单体流程已经达到边界

### 纠偏
- 误区：多 agent 不是高级感按钮
- 为什么会出问题：多 agent 会带来更多调度、可观测性、成本和状态一致性问题
- 替代思路：先用单 agent 或 workflow 验证收益，再决定是否拆角色

## 5. 只讲 happy path，不讲 failure path

### 识别信号
- 方案只描述“正常工作时如何运行”
- 没有超时、空检索、工具失败、冲突状态、错误恢复

### 纠偏
- 误区：你在设计 demo，不是在设计系统
- 为什么会出问题：AI 系统一进入真实数据和真实用户就会频繁进入异常分支
- 替代思路：每个关键模块都补一个“最可能怎么失败”

## 6. 只给代码，不给模块边界

### 识别信号
- 用户要求“直接给我代码”
- 方案中没有模块职责说明

### 纠偏
- 误区：代码不是系统结构的替代品
- 为什么会出问题：边界不清时，代码只会把混乱写死
- 替代思路：先定义模块职责和接口，再写最小实现

## 7. 只说“效果好”，不讲评估

### 识别信号
- 用户用“更智能”“效果更好”“体验更顺”描述目标
- 没有指标、样本、对照或测试场景

### 纠偏
- 误区：没有评估就没有“更好”
- 为什么会出问题：你无法区分偶然命中和系统改进
- 替代思路：先定义任务成功标准，再设计评测样本和对照

## 8. 为高级感过度设计

### 识别信号
- 一上来就要长期记忆、知识图谱、多 agent、反思、自治规划
- 但用户需求其实只是稳定调用几类工具

### 纠偏
- 误区：你在为想象中的复杂度付费
- 为什么会出问题：过度设计增加维护成本，也让定位问题更难
- 替代思路：先做能验证关键假设的 MVP，保留未来演化接口即可

## 9. 将模型能力误认为系统能力

### 识别信号
- 用户认为模型“会推理”，系统就天然可靠
- 用户认为模型知道工具的真实状态

### 纠偏
- 误区：模型能力不等于系统保证
- 为什么会出问题：系统真正可靠性来自工具契约、状态一致性、检索质量、回退策略和评估
- 替代思路：把模型看成一个强但不可靠的组件，再围绕它设计控制层
